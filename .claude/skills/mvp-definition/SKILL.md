## Instructions

You are helping define or evaluate an MVP (Minimum Viable Product). The goal is to ship the smallest thing that tests the core hypothesis and provides real value to users.

### MVP Principles

- An MVP is NOT a prototype. It MUST be production-quality within its scope.
- An MVP is NOT version 1.0. It is the smallest subset of v1.0 that is independently valuable.
- The goal is to learn, not to impress. Ship the minimum, measure, iterate.
- Every feature in the MVP MUST directly support the core value proposition.

### Scoping Protocol

**Step 1 — Identify the Core Hypothesis**
- What problem are we solving?
- For whom?
- What is the ONE thing this product must do well to be worth using?

**Step 2 — List All Desired Features**
- List everything stakeholders want in the initial release.
- Do not filter yet — capture the full wishlist.

**Step 3 — Classify Each Feature**
- **Must-have** — without this, the product does not solve the core problem.
- **Should-have** — significantly improves the product but is not essential.
- **Nice-to-have** — would be good eventually but does not affect core value.
- **Out of scope** — explicitly not part of this product.

**Step 4 — Challenge Every Must-Have**
- For each must-have: "If we shipped without this, would anyone use the product?"
- If the answer is "yes, but it would be harder" — it is a should-have, not a must-have.
- The MVP MUST contain only true must-haves.

**Step 5 — Define the Cut Line**
- The MVP scope is the must-have list ONLY.
- Everything else goes on the roadmap with prioritization.
- Document what was explicitly excluded and why.

### Common Mistakes

- Flag "MVP" plans that are actually full products — if the MVP takes more than 4-8 weeks with a small team, it is too big.
- Flag missing feedback mechanisms — if the MVP does not include a way to collect user feedback, it fails at its primary purpose.
- Flag perfectionism masquerading as quality — the MVP does not need a design system, animation library, or custom icon set.
- Flag technical over-engineering — use the simplest stack that works. Migrate later if needed.

### Output

- State the core hypothesis in one sentence.
- List must-haves with justification for each.
- List what was cut and why.
- Estimate timeline and team size.
- Define success metrics — how will we know the MVP worked?
